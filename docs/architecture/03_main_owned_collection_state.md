# Main-Owned Collection State

The main process is the single source of truth for the currently open collection. The renderer holds
a read-only replica that it updates from patches broadcast by main, plus purely visual UI state
(selection, open folders, sort mode, …).

## Why

Previously the collection existed three times: on disk, as `EnvironmentService._currentCollection`
in main, and spread over three renderer stores (collection, variable, environment). Changes reached
main in three different ways (store first then IPC, IPC first, or reload everything), and main
mutated objects it received from the renderer. Request edits only reached main when a Monaco model
was disposed. The nested `children` tree and the id Maps in the renderer drifted apart.

## Model

`src/shim/collection-model/` defines the normalized model shared by both processes:

```ts
interface CollectionModel {
  version: number; // incremented by every applied command
  collection: CollectionInfo; // Collection without `children`
  selectedEnvironmentKey?: string; // session-only, not persisted
  folders: Map<string, FolderInfo>; // Folder without `children`
  requests: Map<string, TrufosRequest>; // current state (the draft if there is one)
  savedRequests: Map<string, TrufosRequest>; // saved state of requests that have a draft
  childIds: Map<string, string[]>; // parent id -> ordered child ids
}
```

Order and nesting are stored exactly once, in `childIds`. `parentId` on a node must always match the
`childIds` entry that contains it. Text bodies and scripts are **not** part of the model; they live
in files and in the renderer's Monaco models.

## Commands

Every change to the model is a `CollectionCommand`, a Zod discriminated union in
`src/shim/collection-model/commands.ts`, discriminated by the `CommandType` enum. Requests are
changed with `editRequest`, the collection's own settings (title, variables, environments, client
certificate, authorization) with `updateCollection`. Both take a `...Changes` object in which
`undefined` leaves a field untouched and `null` removes it, applied by `assignChanges()`; adding an
editable field is one line in the schema. Commands are wrapped in an envelope carrying a command id
and a timestamp. `applyCommand(model, envelope)` is a pure Immer recipe used by **both** processes,
so they cannot disagree about what a command does. Anything non-deterministic (new ids, timestamps)
is part of the command, generated by the sender. Bulk operations (`move`, `delete`, `copy`) take a
list of top-level ids and are applied as one command, so in the model they either happen completely
or not at all. On disk, a move or delete of several items can fail halfway; the reload after the
failure then shows the partial state.

## Flow

```
renderer action ──▶ applyCommand (optimistic, pending) ──▶ IPC dispatch(envelope)
                                                              │
main: Zod parse ─▶ produceWithPatches(applyCommand) ─▶ broadcast {patches, version, commandId}
                                                   └─▶ persistence effect (serial queue)
renderer: applyPatches(confirmed) ─▶ drop own pending command ─▶ re-apply remaining pending
```

- **Main** (`CollectionStateService`) validates, applies, broadcasts and persists. Which files a
  command writes is decided by `getCommandEffects()`
  (`src/main/collection-state/command-effects.ts`), the only place that knows what a command type
  means for the disk. It returns `immediate` writes (structural operations: create, move, rename,
  delete, copy, save, discard) and, for request edits, a `dirtyRequestId`: the info file of a dirty
  request is written from the current model 2 s after its last edit, or earlier when something
  flushes. Text body and script edits mark the request dirty as well, so the modification time of
  its info file follows them. A request stays dirty until its info file was written: if that
  fails, the reload after the failure retries it first, so the edit survives if possible. A dirty
  request that was deleted meanwhile is skipped. Effects that write the info file of a request
  themselves (creating, saving or discarding a draft) mark it clean, so it is not written twice. A request that becomes a draft gets its draft directory first, whatever the
  command was; this is derived from the model transition, not restated per command. The service
  itself is command-agnostic: everything runs on one serial queue, in order: writes, readers, and
  loading another collection. Dirty requests are written before a request is sent, before the app
  closes and before the collection changes. If a persistence effect fails, main reloads the
  collection from disk and broadcasts a snapshot; effects that were queued before the failure are
  skipped, whether or not the reload succeeds, as they were planned from a model that no longer
  matches the disk. Commands that arrive while a collection is being loaded are rejected. The
  debounce only protects against crashes: every path that reads a request from disk flushes first.
  Directory names are chosen so that they neither collide with a known object nor with a directory
  that happens to exist on disk, e.g. one left over from a crash.
- **Renderer** (`CollectionState`, mirrored into the zustand collection store) keeps the last
  confirmed model and a queue of pending (sent, unconfirmed) commands. The visible state is the
  confirmed model with the pending commands re-applied. When main confirms the oldest pending
  command, the visible model stays as it is (both were computed by the same `applyCommand`), so
  the common case costs one render, not two, even while typing. If a command is rejected or a
  version is skipped, the renderer fetches a fresh snapshot; a snapshot that is older than one
  broadcast meanwhile is ignored.
- Opening, creating, importing or closing a collection broadcasts a full snapshot.

## Drafts

A request has a draft when `requests.get(id).draft` is true; its saved state is in `savedRequests`
(absent for a request that was never saved). On disk, drafts keep the `.draft/` layout. When a draft
is first created, main copies the saved body and scripts into `.draft/`, so the draft directory is
always complete.

The text body and the scripts have one owner: the Monaco models in the renderer. Edits are sent as
debounced (1 s) `setTextBody` / `setScript` commands. The first edit sends `createDraft` right away,
so the request shows as changed at once. The operations that need the editor content flush it
themselves: sending, saving, copying, switching request or collection, and closing. Disposing a
Monaco model only frees memory. While the content of a model is loaded, or while the changes of its
request are discarded, changes to it are not edits: the loaded content replaces them, and sending
them would persist a fragment instead of the whole text. If a debounced edit is rejected, the user
is told and the model is reloaded from disk, so the editor never silently shows unsaved text.

## Other main services

- `EnvironmentService` resolves variables and authorization from the model.
- `ScriptingService` runs a script against an Immer draft of the collection. Scripts run
  synchronously, so the model cannot change meanwhile. Afterwards, the changed variables are
  applied with one `updateCollection` command. The model changes synchronously; the script does
  not wait for the collection file to be written.
- `HttpService.sendRequest()` and `stream-open` take request ids; main looks the request up in its
  model (`CollectionStateService.prepareRequest()` and `readRequest()`) and opens its files on the
  persistence queue, so no write interleaves. Everything else a request needs, e.g. variables and
  the client certificate, is read from the current model while it is sent. The prepared request
  carries the id of its collection: if another collection was opened meanwhile, its scripts are not
  run (a warning goes to the script log) and it fails instead of being dispatched.
  `PersistenceService` opens a file before it returns the stream, so once a reader got its stream,
  later writes cannot change what it reads. A request reads its scripts and opens its text body
  before it is sent (`PersistenceService.openRequestFiles()`), together with the collection it
  belongs to; the body is streamed, never read into memory. Text bodies and JSON files are written
  atomically (a temporary file replaces the target, `PersistenceService.replaceFile()`), so readers
  never see a half-written file and a request that is being sent keeps streaming the body it was
  sent with.
