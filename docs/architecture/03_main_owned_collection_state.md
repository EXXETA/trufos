# Main-Owned Collection State

The main process is the single source of truth for the currently open collection. The renderer
holds a read-only replica that it updates from patches broadcast by main, plus purely visual UI
state (selection, open folders, sort mode, …).

## Why

Previously the collection existed three times: on disk, as `EnvironmentService._currentCollection`
in main, and spread over three renderer stores (collection, variable, environment). Changes reached
main in three different ways (store first then IPC, IPC first, or reload everything), and main
mutated objects it received from the renderer. Request edits only reached main when a Monaco model
was disposed. The nested `children` tree and the id Maps in the renderer drifted apart.

## Model

`src/shim/collection-model/` defines the normalized model shared by both processes:

```ts
interface CollectionModel {
  version: number; // incremented by every applied command
  collection: CollectionInfo; // Collection without `children`
  selectedEnvironmentKey?: string; // session-only, not persisted
  folders: Map<string, FolderInfo>; // Folder without `children`
  requests: Map<string, TrufosRequest>; // current state (the draft if there is one)
  savedRequests: Map<string, TrufosRequest>; // saved state of requests that have a draft
  childIds: Map<string, string[]>; // parent id -> ordered child ids
}
```

Order and nesting are stored exactly once, in `childIds`. `parentId` on a node must always match the
`childIds` entry that contains it. Text bodies and scripts are **not** part of the model; they live
in files and in the renderer's Monaco models.

## Commands

Every change to the model is a `CollectionCommand`, a Zod discriminated union in
`src/shim/collection-model/commands.ts`, discriminated by the `CommandType` enum. Requests are
changed with `editRequest`, the collection's own settings (title, variables, environments, client
certificate, authorization) with `updateCollection`. Commands are wrapped in an envelope carrying a command id
and a timestamp. `applyCommand(model, envelope)` is a pure Immer recipe used by **both** processes,
so they cannot disagree about what a command does. Anything non-deterministic (new ids, timestamps)
is part of the command, generated by the sender.

## Flow

```
renderer action ──▶ applyCommand (optimistic, pending) ──▶ IPC dispatch(envelope)
                                                              │
main: Zod parse ─▶ produceWithPatches(applyCommand) ─▶ broadcast {patches, version, commandId}
                                                   └─▶ persistence effect (serial queue)
renderer: applyPatches(confirmed) ─▶ drop own pending command ─▶ re-apply remaining pending
```

- **Main** (`CollectionStateService`) validates, applies, broadcasts and persists. Which files a
  command writes is decided by `getCommandEffects()` (`src/main/collection-state/command-effects.ts`).
  The effects run on one serial queue. Request edits are written debounced (2 s) per request;
  structural
  operations (create, move, rename, delete, copy, save, discard) are written immediately. Pending
  writes are flushed before a request is sent, before the app closes and before the collection
  changes. If a persistence effect fails, main reloads the collection from disk and broadcasts a
  snapshot. Commands that arrive while a collection is being loaded are rejected.
  The debounce only protects against crashes: every path that reads a request from disk flushes
  first.
- **Renderer** keeps the last confirmed model and a queue of pending (sent, unconfirmed) commands.
  The visible state is the confirmed model with the pending commands re-applied. If a command is
  rejected or a version is skipped, the renderer fetches a fresh snapshot.
- Opening, creating, importing or closing a collection broadcasts a full snapshot.

## Drafts

A request has a draft when `requests.get(id).draft` is true; its saved state is in
`savedRequests` (absent for a request that was never saved). On disk, drafts keep the `.draft/`
layout. When a draft is first created, main copies the saved body and scripts into `.draft/`, so
the draft directory is always complete.

The text body and the scripts have one owner: the Monaco models in the renderer. Edits are sent as
debounced (1 s) `setTextBody` / `setScript` commands, which are flushed before sending, saving, switching
request or collection, and closing. Disposing a Monaco model only frees memory.

## Other main services

- `EnvironmentService` resolves variables and authorization from the model.
- `ScriptingService` works on a copy of the variables while a script runs. Afterwards, it applies
  only the variables the script set onto the current model with one `updateCollection` command.
- `sendRequest` and `stream-open` take request ids; main looks the request up in its model and
  opens its files on the persistence queue, so no write interleaves. A request reads its scripts
  and opens its text body before it is sent; the body is streamed, never read into memory. Text
  bodies are written atomically (a temporary file replaces the body file), so a request that is
  being sent keeps streaming the body it was sent with.
