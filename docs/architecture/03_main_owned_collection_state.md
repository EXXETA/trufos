# Main-Owned Collection State

The main process is the single source of truth for the currently open collection. The renderer holds
a read-only replica that it updates from patches broadcast by main, plus purely visual UI state
(selection, open folders, sort mode, …).

## Why

Previously the collection existed three times: on disk, as `EnvironmentService._currentCollection`
in main, and spread over three renderer stores (collection, variable, environment). Changes reached
main in three different ways (store first then IPC, IPC first, or reload everything), and main
mutated objects it received from the renderer. Request edits only reached main when a Monaco model
was disposed. The nested `children` tree and the id Maps in the renderer drifted apart.

## Model

`src/shim/collection-model/` defines the normalized model shared by both processes:

```ts
interface CollectionModel {
  version: number; // incremented by every applied command
  collection: CollectionInfo; // Collection without `children`
  selectedEnvironmentKey?: string; // stored in the app state, not in the collection
  folders: Map<string, FolderInfo>; // Folder without `children`
  requests: Map<string, TrufosRequest>; // current state (the draft if there is one)
  savedRequests: Map<string, TrufosRequest>; // saved state of requests that have a draft
  childIds: Map<string, string[]>; // parent id -> ordered child ids
}
```

Order and nesting are stored exactly once, in `childIds`. `parentId` on a node must always match the
`childIds` entry that contains it. Text bodies and scripts are **not** part of the model; they live
in files and in the renderer's Monaco models.

## Commands

Every change to the model is a `CollectionCommand`, a Zod discriminated union in
`src/shim/collection-model/commands.ts`, discriminated by the `CommandType` enum. Requests are
changed with `editRequest`, the collection's own settings (title, variables, environments, client
certificate, authorization) with `updateCollection`. Both take a `...Changes` object in which
`undefined` leaves a field untouched and `null` removes it, applied by `assignChanges()`; adding an
editable field is one line in the schema. `updateCollection` also selects the environment
(`selectedEnvironmentKey`, `null` for none), as the selection belongs to the model but is not
written to the collection; a command that only selects one has empty `changes` and writes nothing
to the collection. Instead, `CollectionStateService` stores the selection of every command that
changes it with the open collection in the app state (see below). When it loads the collection,
it selects the stored environment, so the snapshot already has it; a collection without one, or
whose stored environment no longer exists, starts with its first environment. Commands are
wrapped in an envelope carrying a command id and a timestamp. `applyCommand(model, envelope)` is a
pure Immer recipe used by **both** processes, so they cannot disagree about what a command does.
Anything non-deterministic (new ids, timestamps) is part of the command, generated by the sender.
Bulk operations (`move`, `delete`, `copy`) take a list of top-level ids and are applied as one
command, so in the model they either happen completely or not at all. On disk, a move or delete of
several items can fail halfway; the reload after the failure then shows the partial state.

## Flow

```
renderer action ──▶ applyCommand (optimistic, pending) ──▶ IPC dispatch(envelope)
                                                              │
main: Zod parse ─▶ produceWithPatches(applyCommand) ─▶ broadcast {patches, version, commandId}
                                                   └─▶ persistence effect (serial queue)
renderer: applyPatches(confirmed) ─▶ drop own pending command ─▶ re-apply remaining pending
```

### Main

`CollectionStateService` validates, applies, broadcasts and persists.

- **One queue.** The service is command-agnostic. Everything that changes the model or touches
  the files runs as one task after another on a single queue (`SerialQueue`,
  `src/main/util/serial-queue.ts`): applying a command together with its immediate effect,
  delayed writes, readers, and loading another collection. So an effect is always written from the
  model it was planned from, and nothing has to be skipped or rolled back later.
- **Effects.** `getCommandEffects()` (`src/main/collection-state/command-effects.ts`) is the only
  place that knows what a command type means for the disk. It returns `immediate` writes for
  structural operations (create, move, rename, delete, copy, save, discard) and, for request
  edits, a `dirtyRequestId`. A request that becomes a draft gets its draft directory first,
  whatever the command was; this is derived from the model transition, not restated per command.
- **Dirty requests.** The info file of a dirty request is written from the current model 2 s after
  its last edit, or earlier when something flushes: before a request is sent, before the app
  closes and before the collection changes. Text body and script edits mark the request dirty as
  well, so the modification time of its info file follows them. A request stays dirty until its
  info file was written; a dirty request that was deleted meanwhile is skipped. Effects that write
  the info file themselves (creating, saving or discarding a draft) mark it clean, so it is not
  written twice. The debounce only protects against crashes: every path that reads a request from
  disk flushes first.
- **Failures.** If a persistence effect fails, main reloads the collection from disk and
  broadcasts a snapshot before the next task runs. The reload writes the dirty requests first, so
  their edits survive if possible.
- **Collection changes.** A command that was dispatched while a collection is loaded is applied to
  the loaded model afterwards, or rejected with a `CollectionChangedError` if another collection
  is open by then. Opening, creating or closing a collection broadcasts a full snapshot. An import
  only writes the collection; the renderer then opens it.
- Directory names are chosen so that they neither collide with a known object nor with a
  directory that happens to exist on disk, e.g. one left over from a crash.

### Renderer

`CollectionState`, mirrored into the zustand collection store, keeps the last confirmed model and
the pending (sent, unconfirmed) commands. The visible state is the confirmed model with the
pending commands re-applied.

- **Confirmation.** When main confirms the oldest pending command, the visible model stays as it
  is (both were computed by the same `applyCommand`), so the common case costs one render, not
  two, even while typing.
- **Replies before patches.** The IPC does not order the reply of a dispatch and the broadcast of
  its patches, so the reply can arrive first. The reply carries the version main applied the
  command as; the command stays pending until its patches arrive, and a snapshot of that version
  or later already contains it.
- **Resync.** If a command is rejected or a version is skipped, the renderer fetches a fresh
  snapshot. Patches that arrive meanwhile are held back and applied on top of it, unless it
  already contains them. A snapshot that is older than one broadcast meanwhile is ignored.
- **UI state.** The renderer owns the visual state of a collection that is restored when it is
  opened again: the selected request, the open folders, the sort mode and the script tab
  (`CollectionUiState`, `src/shim/collection-ui-state.ts`). Main stores it with the open
  collection in the app state, so there is one owner of everything kept per collection, and
  closing a collection forgets all of it at once. The store sends changes to main 500 ms after the
  last one (`src/renderer/state/helper/collection-ui-state.ts`), and right away before the window
  closes or another collection is opened. A snapshot carries the stored UI state, so the store
  restores it, pruned to IDs that still exist, before the first render and when another
  collection is opened. The request is opened like any other selection, so its editor models
  load. Switching collections only flushes the editor changes; the selection changes once main
  broadcast the other collection. An edit typed in between is dropped with the editor models, or
  rejected by main if its debounce ran out before. The sizes of the resizable panels are not per
  collection; react-resizable-panels keeps them in `localStorage`.

## Drafts

A request has a draft when `requests.get(id).draft` is true; its saved state is in `savedRequests`
(absent for a request that was never saved). On disk, drafts keep the `.draft/` layout. When a draft
is first created, main copies the saved body and scripts into `.draft/`, so the draft directory is
always complete.

The text body and the scripts have one owner: the Monaco models in the renderer. Edits are sent as
debounced (1 s) `setTextBody` / `setScript` commands. The first edit sends `createDraft` right away,
so the request shows as changed at once. The operations that need the editor content flush it
themselves: sending, saving, copying, switching request or collection, and closing. Disposing a
Monaco model only frees memory. While the content of a model is loaded, changes to it are not edits:
the loaded content replaces them, and sending them would persist a fragment instead of the whole
text. Discarding the changes of a request uses the same rule: the saved content is loaded once main
discarded the changes, so text typed meanwhile is replaced instead of sent. If a debounced edit is
rejected, the user is told and the model is reloaded from disk, so the editor never silently shows
unsaved text.

## Changes outside the app

The files of a collection may change outside the app, e.g. by a branch switch or a pull.
`CollectionStateService` watches the directory of the open collection with a `CollectionWatcher`
(`fs.watch` with `recursive`), which it points at every collection it installs. The watcher reports
the changed files together once no change came for 300 ms. It only watches what git versions: the
files the app adds to the `.gitignore` of a collection (`GIT_IGNORE_LINES`: drafts, secrets and the
temporary files of `replaceFile()`) are the ones only the app writes, so `isAppOwnedPath()`
(`persistence-service.ts`) ignores exactly these. Every edit of a request makes it a draft first,
so editing writes only into `.draft/` and causes no reports at all.

A report (`FileChanges`) has the paths of the changed files the platform named, and whether a change
came without a file name (`unnamed`). If only text bodies and scripts changed (`isContentFile()`),
the collection cannot have changed, as they are not part of the model. Otherwise, or if any change
was unnamed, the service runs `reloadIfChanged()`: it reads the collection into a new model and compares it with the
current one, leaving out the version and the modification times. In the current model a node has
the time of its last command, in a read model the modification time of its info file. Reading the
files the app wrote itself gives the same model, so the app's own writes, e.g. a rename or a save,
broadcast nothing. Otherwise the read model is installed and broadcast as a snapshot. Dirty
requests are written first, so an edit made in the app wins over a change of the same request
outside it.

The saved requests whose text body or script changed are announced as
`MainProcessEvent.RequestFilesChanged` (`PersistenceService.requestsOfContentFiles()`), also if the
reload failed, as they do not depend on it: a broken info file does not keep the editors from
following a branch switch. If one is
the selected request, the renderer refreshes its editors with `refreshModelContent()`. It replaces
the content only if it changed and the user did not edit the editor meanwhile, so nothing typed is
lost. Saving or copying a request writes these files too, so the renderer also gets its own
changes and finds them equal to its editors; this is accepted rather than tracking which files main
wrote itself.

A watcher can miss changes or fail, e.g. at the inotify limit on Linux; a failure is only logged.
As a fallback, the renderer keeps the files and the app in sync around the focus of the window
(`CollectionStoreProvider`): when it loses focus, the editor changes are sent and main writes the
dirty requests (`IEventService.flushCollection()`); when it gets focus back, `checkForChanges()`
lets main reload if the collection changed (`reloadCollectionIfChanged()`) and refreshes the editors
of the selected request in any case, as main cannot tell whether its text body or scripts changed.
**Collection > Reload from Disk** (`reloadFromDisk()`) does the same, but main reloads
unconditionally. While the watcher runs, the focus check and a watcher report may refresh the same
editor; that is harmless, as a refresh with equal content does nothing.

If the files cannot be read, e.g. because of merge conflict markers, the current model stays and
the next change or focus tries again. The check on focus and the menu show the error to the user;
after a watcher report it is only logged, as main cannot show it. Edits keep being saved, so editing
a request whose file is broken overwrites it with the state of the app.

## Other main services

- Main keeps two JSON files of the application in `userData`. Each service holds a `JsonFile`
  (`src/main/persistence/json-file.ts`) privately and offers the operations on its content.
  `JsonFile` migrates older versions, validates the content with Zod whenever it is read or
  changed, keeps it immutable in memory and reads and writes the file one at a time, replacing it
  atomically. `settings.json` (`SettingsService`) has the preferences the user chooses.
  `state.json` (`StateService`) has the state of the application: the open collections with the
  selected environment (`null` for none) and the UI state of each, and the current collection.
  Its rules (the default collection is always open, the current collection is one of the open
  ones) are part of its schema, so they hold after every change.

- `variable-resolver.ts` (`src/main/environment/service/`) resolves variables and authorization
  from a model it is given; it never reads the current model itself.
- `ScriptingService` runs a script against an Immer draft of the collection. The script and the
  one `updateCollection` command for the variables it changed run as a single task on the
  collection state's queue (`CollectionStateService.applyTo()`), so the model cannot change in
  between. `applyTo()` returns the model after the command. If another collection is open by
  then, it throws a `CollectionChangedError`, as `dispatch()` does; this is the only place that
  rule lives. The script waits for the collection file to be written; a failure is only logged.
- `HttpService.sendRequest()` and `stream-open` take request ids; main looks the request up in its
  model (`CollectionStateService.prepareRequest()` and `readRequest()`) and opens its files on the
  persistence queue, so no write interleaves. The prepared request carries the model it was taken
  from. The pre-request script runs first and returns the model it left behind; the URL,
  authorization, headers, body variables and client certificate are all resolved from that one
  model, so a token the script sets is used by the request. `PersistenceService` opens a file before
  it returns the stream, so once a reader got its stream, later writes cannot change what it reads.
  A request reads its scripts and opens its text body before it is sent
  (`PersistenceService.openRequestFiles()`), together with the model it belongs to; the body is
  streamed, never read into memory. Text bodies, scripts, JSON files and secrets files are written
  atomically (a temporary file replaces the target, `FileSystemService.replaceFile()`), so readers
  never see a half-written file and a request that is being sent keeps streaming the body it was
  sent with.
